# Toasts

Push notifications to your visitors with a toast, a lightweight and easily customizable alert message.

Toasts are lightweight notifications designed to mimic the push notifications that have been popularized by mobile and desktop operating systems. They’re built with flexbox, so they’re easy to align and position.

## Overview

Things to know when using the `Toast` model:

- Toasts are opt-in: create a `Toast` model and mount its `Component` before calling `open()`.
- Toasts automatically hide after `delay` milliseconds; pass `delay: 0` to keep one visible until it is dismissed.

The animation effect of this component is dependent on the `prefers-reduced-motion` media query.

## Examples

### Basic

To encourage extensible and predictable toasts, we recommend a header and body. Toast headers use `display: flex`, allowing easy alignment of content thanks to our margin and flexbox utilities.

Toasts are as flexible as you need and have very little required markup. At a minimum, we require a single element to contain your “toasted” content and strongly encourage a dismiss button.

<CodeExample>
    <StaticToast body="Hello, world! This is a toast message." />
</CodeExample>

By default, toasts fade in and out. To disable the animation, pass `instant` to `ToastItem` or `Toast.open()`. The toast then appears without the CSS transition.

## Placement

Place toasts with custom CSS as you need them. The top right is often used for notifications, as is the top middle. Use the `position` prop on `ToastContainer` or `toast.Component` for a standard viewport position. If you’re only ever going to show one toast at a time, put the positioning styles right on `ToastItem`.

## Accessibility

Toasts are intended to be small interruptions to your visitors or users, so to help those with screen readers and similar assistive technologies, you should wrap your toasts in an [`aria-live` region][5]. Changes to live regions (such as injecting/updating a toast component) are automatically announced by screen readers without needing to move the user’s focus or otherwise interrupt the user. Additionally, include `aria-atomic="true"` to ensure that the entire toast is always announced as a single (atomic) unit, rather than just announcing what was changed (which could lead to problems if you only update part of the toast’s content, or if displaying the same toast content at a later point in time). If the information needed is important for the process, e.g. for a list of errors in a form, then use the [alert component][6] instead of toast.

Note that the live region needs to be present in the markup _before_ the toast is generated or updated. If you dynamically generate both at the same time and inject them into the page, they will generally not be announced by assistive technologies.

You also need to adapt the `role` and `aria-live` level depending on the content. If it’s an important message like an error, use `role="alert" aria-live="assertive"`, otherwise use `role="status" aria-live="polite"` attributes.

<CodeExample>
    <ToastContainer position="static" aria-live="polite" aria-atomic="true">
        <StaticToast live="polite" body="A polite status update with enough time to read." />
    </ToastContainer>
</CodeExample>

As the content you’re displaying changes, be sure to update the [`delay` timeout][7] so that users have enough time to read the toast.

When using `delay: 0`, you must add a close button to allow users to dismiss the toast.

<CodeExample source="document/component/Documentation/Components/ToastDemo.tsx">
    <ToastMessageDemo
        label="Show persistent toast"
        delay={0}
        body="This toast stays visible until you close it."
    />
</CodeExample>

While technically it’s possible to add focusable/actionable controls (such as additional buttons or links) in your toast, you should avoid doing this for autohiding toasts. Even if you give the toast a long [`delay` timeout][7], keyboard and assistive technology users may find it difficult to reach the toast in time to take action (since toasts don’t receive focus when they are displayed). If you absolutely must have further controls, we recommend using a toast with `delay: 0`.

## Usage

Create a `Toast` model and mount its `Component` to establish the live region before showing notifications. Call `open({ title, body, delay })` to append a toast. The live example above demonstrates this React integration.

### Options

| Message option | Default    | Description                                                                |
| -------------- | ---------- | -------------------------------------------------------------------------- |
| `body`         | required   | Toast body as a React node.                                                |
| `title`        | —          | Optional toast heading.                                                    |
| `delay`        | `3000`     | Milliseconds before hiding; `0` disables automatic dismissal.              |
| `id`           | generated  | Supply an ID to replace an existing notification or dismiss it later.      |
| `role`         | `"status"` | Use `"alert"` for urgent messages and an appropriate live-region priority. |
| `theme`        | —          | Contextual theme color.                                                    |
| `translucent`  | `false`    | Blur and saturate the background.                                          |
| `instant`      | `false`    | Skip the CSS transition.                                                   |

### Methods

`open(message)` returns a promise that resolves when that notification closes. Call `close(id)` to dismiss an individual notification.
